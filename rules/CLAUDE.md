# CLAUDE.md - Senior Engineering Discipline & Anti-Hallucination Protocol

> Drop this file into your project root. Works out of the box with Claude Code, Cursor (`.cursorrules`), Pi, Codex, and OpenCode.

## 0. THE PRIME DIRECTIVES (NON-NEGOTIABLE)

1. **MINIMAL SURGICAL EDITS**: Never touch lines of code that do not strictly need changing. Do not reformat unchanged functions, do not reorder imports unless asked, do not "tidy up" surrounding code.
2. **NO PHANTOM FIXES**: Never assume a fix worked without concrete verification. If a test or command exists, run it. If there is a compiler/linter error, resolve the root cause—never suppress it with `any`, `@ts-ignore`, `unwrap()`, or empty `catch` blocks.
3. **NEVER HALLUCINATE PACKAGES**: Do not invent NPM/Cargo/PyPI libraries or methods. If unsure whether an API exists in a library version, check the local `node_modules`, `Cargo.lock`, or documentation before writing code.
4. **ASK BEFORE REFACTORING**: If you believe an architectural change or third-party dependency is required to solve the task, STOP and explain why first. Do not add dependencies or re-architect unilaterally.

---

## 1. CODE EDITING DISCIPLINE

- **Preserve Existing Patterns**: Mirror the naming conventions, error-handling idioms, and module layout of the host codebase.
- **Diff Minimization**: Your PR/diff should be easy for a human to review. A 2-line bug fix must NEVER result in a 50-line diff.
- **Fail Loudly & Explicitly**: Avoid silent fallbacks. When an invariant is broken, surface the error clearly instead of returning default mock objects that mask failures downstream.

---

## 2. THE 4-STEP EXECUTION PROTOCOL

When given a coding or debugging task, always follow this sequence:

1. **Investigate (Read-Only)**:
   - Read the relevant files first. Check call sites and imports.
   - Trace the actual data flow rather than guessing from function names.
2. **Hypothesize**:
   - Formulate a specific hypothesis about the root cause or required change.
3. **Surgically Implement**:
   - Apply the minimal change required to satisfy the requirement or resolve the bug.
4. **Empirically Verify**:
   - Run tests, compilers, or diagnostics. If something fails, do NOT guess again—read the error output thoroughly before taking the next action.

---

## 3. ZERO-AI-SLOP RULES (PROHIBITED HABITS)

- ❌ NEVER generate mock data placeholders (`// TODO: implement real logic`) inside what should be production code.
- ❌ NEVER delete comments, copyright notices, or existing type definitions without explicit instructions.
- ❌ NEVER replace working concrete implementations with generic over-abstracted classes, factory patterns, or unnecessary wrappers.
- ❌ NEVER write speculative code for "future extensibility" that was not requested.

## 4. CONTEXT ECONOMY & PROGRESSIVE DISCLOSURE

- **Progressive Discovery**: Do not dump 1,000+ line files into the conversation context. Use `rg` or symbol search first, inspect the target function or interface slice with line offsets, and read the entire file only when structural refactoring is explicitly necessary.
- **Isolate Noisy Operations**: Run broad exploratory regex searches, heavy test suites, or large log dumps in sub-shells or isolated tool calls. Never pollute the primary conversation history with thousands of lines of terminal output.
- **The 3-Attempt Circuit Breaker**: If a compilation error or failing test is not resolved after 3 consecutive edits, STOP immediately. Do not make speculative random changes. Revert unverified edits (`git checkout -- <file>`), formulate a new root-cause hypothesis, or present the diagnostic findings to the user.
- **Prompt Prefix Cache Awareness**: Keep static repository guidelines and rules unchanged at the prompt prefix to benefit from KV cache acceleration. Append dynamic context, execution results, and diffs strictly to the tail.
- **Memory Bank & Compacting Protocol**: In complex multi-turn sessions, maintain a rolling compact state (`[Goal] -> [Verified Ground Truth] -> [Applied Diffs] -> [Next Action]`). When context approaches capacity, compress conversation turns into dense structured milestones to eliminate "Lost in the Middle" attention degradation.
- **Bounded Diagnostic Truncation**: When running tests or linters, extract only the failing trace and line numbers. Never ingest 500 lines of passing green tests into prompt memory.
- **MCP & Tool Calling Payload Virtualization**: When calling Model Context Protocol (MCP) servers or CLI tools that return multi-entity records, enforce bounded pagination (`limit <= 25`), select projections, and summarize data at the tool layer. Never pull megabytes of raw JSON responses into LLM context window memory.
- **Dynamic Tool Schema Loading**: For large toolsets (>25 tools), defer loading full JSON schemas into the active context until the tool category is explicitly activated, avoiding prompt token exhaustion.
- **Bitwise Cache Invariance**: Ensure instructions, schemas, and memory banks remain bitwise immutable across turns to maintain hardware KV cache prefix hits (Anthropic prompt caching, OpenAI prefix cache, vLLM RadixAttention).

## 5. EXECUTION & CLI DISCIPLINE

- **Non-Interactive Execution**: Always pass non-interactive flags (`-y`, `--yes`, `CI=true`) to package managers, migrations, and CLI tools to avoid hanging on unanswerable interactive prompts.
- **Bounded Command Outputs**: When inspecting logs or running test suites, use targeted filters, line limits, or `head`/`tail` to prevent dumping thousands of lines of terminal output into the context.
- **Clean Subprocess Lifecycles**: Never leave orphan background processes or dangling test servers running; ensure test runs and tools terminate cleanly with deterministic exit codes.
- **Sub-Agent Context Isolation**: Offload heavy exploratory sweeps, repository map generation, and massive benchmark runs to sandboxed sub-agents, returning strictly structured 5-line syntheses to the orchestrator.
- **Git Worktree Isolation for High-Blast-Radius Tasks**: Isolate broad refactoring runs or risky dependency upgrades in ephemeral git worktrees, verifying clean builds before merging to main.
- **Partition-Wise Join & GUC Fencing Discipline**: When generating database queries on partitioned relations, never enable `enable_partitionwise_join` or `enable_partitionwise_aggregate` globally. Scope flags strictly via `SET LOCAL` within transaction boundaries and enforce partition boundary alignment to prevent combinatorial planning storms.
- **Bloom Index & Multi-Facet Search Discipline**: When indexing tables for arbitrary subset equality queries, avoid combinatorial B-Tree sprawl ($2^N$ indexes). Leverage PostgreSQL `bloom` indexes with explicit entropy-calibrated bit allocations ($M \in [256, 1024]$), enforce strict equality (`=`) predicates, and elevate transaction `work_mem` to guarantee lossless bitmap scans (`Lossy: 0`).
- **HypoPG Virtual Index Simulation Discipline**: When diagnosing slow queries or proposing new database indexes, never execute unverified physical DDL (`CREATE INDEX`) directly on staging/production tables. Simulate candidate index hypotheses using PostgreSQL `hypopg` virtual indexes (`SELECT hypopg_create_index(...)`), verify query planner adoption and cost reduction ($\Delta \text{Cost} \ge 60\%$) via `EXPLAIN (FORMAT JSON)` without `ANALYZE`, guarantee session cleanup via `SELECT hypopg_reset()`, and only generate physical migrations using `CREATE INDEX CONCURRENTLY` wrapped in `lock_timeout <= 2000ms`.
- **pg_stat_statements Query Profiling & Regression Containment Discipline**: When diagnosing slow queries or triaging performance regressions, never execute destructive global resets (`SELECT pg_stat_statements_reset()`). Enforce zero-reset differential window snapshots ($\Delta M = M(t_2) - M(t_1)$), profile tail variance using the Coefficient of Variation ($c_v = \text{stddev\_exec\_time} / \text{mean\_exec\_time} \ge 2.0$) to catch parameter sniffing and lock contention masked by global averages, guarantee `track_io_timing = on` to isolate NVMe read/write wait stalls, and enforce zero temp disk spills ($\Delta \text{temp\_blks\_written} = 0$) on all OLTP query paths.
- **auto_explain Execution Plan Logging & Timing Overhead Containment Discipline**: When capturing real-world slow query execution plans in production, always enforce structured JSON emission (`auto_explain.log_format = json`) for lossless machine-verifiable AST parsing. On high-throughput systems, set `auto_explain.log_timing = off` or enforce statistical sampling (`auto_explain.sample_rate <= 0.05`) to eliminate kernel clock timer (`clock_gettime`) CPU overhead in nested loops. Strictly forbid `auto_explain.log_nested_statements = on` without high duration thresholds (>1s) to prevent PL/pgSQL loop log bombs. Mandatory `auto_explain.log_buffers = on` and `auto_explain.log_wal = on` to isolate NVMe disk reads from buffer hits, and use transaction-scoped `SET LOCAL auto_explain.log_min_duration = '50ms'` for canary profiling.
- **pg_stat_io Storage Subsystem & Dirty Buffer Eviction Containment Discipline**: In PostgreSQL 16+, never rely on monolithic OS-level `iostat` or table-level hit aggregates. Use `pg_stat_io` to decompose I/O flux across backend types, targets, and contexts. Enforce Zero Synchronous Client Writes ($\Delta \text{writes} = 0$ for `backend_type = 'client backend'` and `context = 'normal'`) by properly sizing `bgwriter_lru_maxpages`, assert Zero Temp Relation Spills ($\Delta \text{writes} = 0$ for `target = 'temp relation'`) by tuning transaction `work_mem`, and monitor `bulkread` vs `normal` read ratios to immediately catch unindexed sequential table scans.
- **Anti-Join & Semi-Join 3VL NULL Trap & Subquery Unnesting Discipline**: Never write `WHERE id NOT IN (SELECT ...)` subqueries against nullable columns. In SQL three-valued logic, a single `NULL` inside the subquery forces `NOT IN` to evaluate to `UNKNOWN`, causing the query to silently return zero rows while preventing optimizers from unnesting into Hash Anti Joins ($O(N \times M)$ SubPlan fallback). Always enforce `WHERE NOT EXISTS (SELECT 1 FROM ...)` or calibrated `LEFT JOIN ... WHERE right.id IS NULL`. Strictly avoid `SELECT DISTINCT ... JOIN ...` solely to check parent existence; enforce `WHERE EXISTS` to leverage `Hash Semi Join` early short-circuiting and eliminate redundant tuple duplication.
- **pg_repack Online Table Compaction & Exclusive Lock Minimization Discipline**: Permanently prohibit destructive `VACUUM FULL` in production runbooks and agent scripts (`ACCESS EXCLUSIVE` table lockout). For online table and index defragmentation, use `pg_repack` with mandatory pre-flight disk verification (Free Disk Space $\ge 2.2 \times \text{total\_relation\_size}$), assert the target relation possesses a valid `PRIMARY KEY` or `UNIQUE NOT NULL` constraint, parameterize with `--wait-timeout 2` and `--no-kill-backend` to prevent DDL head-of-line blocking storms, monitor replication lag to avoid replica query cancellation cascades, and execute `pg_repack --clean` before and after runs to purge orphaned change-capture triggers and temporary log tables.
- **Hash Join Multi-Batch Spill & Skewed Bucket Elimination Discipline**: When constructing complex multi-table joins or analytical queries, always verify that Hash Join nodes operate in single-batch in-memory mode (`Batches = 1`). Never allow multi-batch Grace Hash Join spills (`Batches > 1` and `temp_blks_written > 0`), which write intermediate batches of inner build and outer probe tuples to physical disk, causing 15x–100x latency spikes and NVMe write thrashing. Enforce single-batch execution using transaction-scoped `SET LOCAL work_mem` and `SET LOCAL hash_mem_multiplier = 2.0`, bounded by a strict session ceiling ($\le 25\%$ available RAM) to protect against postmaster OOM killer termination. Audit join key entropy to eliminate Zipfian bucket hotspots, and ensure table statistics (`ANALYZE`) are fresh so the query planner never inverts join roles by building the hash table on the larger outer relation.
- **Merge Join Presorted Index Scan & Materialize Spill Elimination Discipline**: When designing ordered streams, time-series alignments, or full outer joins, always back join keys with matching B-Tree indexes sharing identical ordering (`ASC/DESC`), `NULLS FIRST/LAST`, and collation (`COLLATE "C"` or deterministic ICU) to achieve zero-sort linear streaming ($O(M+N)$ time, $O(1)$ memory). Never permit external merge sort disk spills (`Sort Method: external merge Disk`) or `Materialize` node buffer spillage (`Temp Written Blocks > 0`). Size transaction-scoped `SET LOCAL work_mem` to absorb peak in-memory quicksorts, and enforce uniqueness (`PRIMARY KEY` or `UNIQUE`) on the inner join relation to eliminate mark-and-restore duplicate run rescans that collapse linear merges into quadratic $O(M \times N)$ nested loops.
- **Nested Loop Parameterized Index Probe & Cardinality Underestimation Defense Discipline**: When designing transactional queries or correlated subqueries (`LATERAL`), always verify that Nested Loop inner relations are backed by selective B-Tree indexes (`Index Scan` or `Index Only Scan`). Strictly forbid unindexed inner sequential scans (`Seq Scan` with `Actual Loops > 1`), which collapse query performance into catastrophic $O(M \times N)$ Cartesian loops. Guard against cardinality underestimation cliffs ($E \ll A$, e.g. 1 row estimated vs 100,000 actual) caused by correlated filters or stale stats, which triggers random I/O thrashing across `shared_buffers`. Ensure high index clustering correlation (`pg_stats.correlation >= 0.8`) or bitmap heap sorting for parameterized inner probes, and assert zero disk spillage on inner `Materialize` nodes (`Temp Written Blocks == 0`).
- **Bitmap Scan Lossy TIDBitmap Degradation & Index Recheck Defense Discipline**: When profiling filtered queries with `Bitmap Heap Scan`, always assert `Lossy Heap Blocks == 0` and `Rows Removed by Index Recheck == 0`. Never permit TIDBitmaps to degrade into lossy page markers due to undersized `work_mem`, which forces the executor to evaluate and discard millions of non-matching tuples on every page (spiking CPU to 100%). Dynamically size transaction-scoped `SET LOCAL work_mem` to comfortably hold exact TIDBitmaps for large scans ($M_{\text{TIDBitmap}} \ge 160 \times P_{\text{match}}$ bytes). Consolidate multi-index `BitmapAnd`/`BitmapOr` intersections into single composite B-Tree indexes `(equality_cols..., range_or_sort_cols...)`, and strictly enforce plain `Index Scan` for `ORDER BY ... LIMIT K` queries to preserve early pipeline termination instead of scanning all matches.
- **HashAggregate Disk Spill & GroupAggregate Streaming Invariants Discipline**: When profiling aggregation queries (`GROUP BY`, `DISTINCT`, rollups), always assert `Batches == 1` and `Disk Usage == 0 kB` for `HashAggregate` execution nodes. Never permit multi-batch disk spills to temp files, which induce 100x p99 latency spikes and NVMe write stalls. Size transaction-scoped `SET LOCAL work_mem` and `SET LOCAL hash_mem_multiplier = 2.0` with $1.5\times$ headroom over estimated hash memory $M_{\text{hash}}(K) \approx K \times (S_{\text{key}} + S_{\text{state}} + 32)$. For high-cardinality groups ($K \ge 100,000$) or paginated `ORDER BY ... LIMIT K` aggregations, deploy composite B-Tree indexes matching grouping expressions to enforce zero-sort, streaming `GroupAggregate` ($O(1)$ memory, instantaneous early termination). Forbid unbounded state accumulators (`jsonb_agg`, `array_agg`) inside HashAggregates without row-limiting fences to prevent postmaster OOM-killer decapitation.
- **Incremental Sort, External Merge Sort Spill & Top-N Heapsort Invariants Discipline**: When designing queries with `ORDER BY`, pagination, or sorted analytical feeds, always verify execution plans assert `Sort Space Type: Memory` and zero disk spillage (`Sort Space Used: 0 kB` on disk). Never permit External Merge Sort disk spills (`Sort Method: external merge Disk`), which trigger multi-pass temporary disk file I/O and degrade tail latency by 50x–200x. For `ORDER BY ... LIMIT K` queries, guarantee Top-N Heapsort preservation (`Sort Method: top-N heapsort`) by eliminating opaque CTE optimization barriers and unpushed window functions, bounding memory to $O(K)$. Exploit PostgreSQL 13+ Incremental Sort (`Incremental Sort`) by aligning composite queries with pre-sorted index prefixes, fencing against low-entropy prefix skew. Accelerate heavy text sorting with explicit `COLLATE "C"` to replace expensive libc `strcoll()` with direct `memcmp()` comparisons, and replace deep `OFFSET` pagination with cursor-based keyset seeks (`WHERE (col, id) < ($c, $i)`).
- **Query Cancellation, Client Disconnect Detection & Timeout Ladder Invariants Discipline**: When building database clients, microservices, or API endpoints connecting to PostgreSQL, always configure active client socket polling (`client_connection_check_interval = '500ms'`) to eliminate phantom query execution after HTTP client or gateway timeouts (where PostgreSQL continues burning 100% CPU on aborted queries for minutes). Enforce the strict 5-tier timeout ladder ($T_{\text{lock\_timeout}} < T_{\text{statement\_timeout}} < T_{\text{transaction\_timeout}} < T_{\text{idle\_in\_transaction}}$) to fail fast on lock contention and prevent head-of-line connection pool exhaustion. Always guarantee immediate deferred `ROLLBACK` in error handlers to purge aborted transactions (`SQLSTATE 25P02`) and release held row/table locks immediately, preventing autovacuum horizon freezing. Never terminate backends with `kill -9` or `SIGQUIT`; always issue `pg_cancel_backend()` (SIGINT) and escalate only to `pg_terminate_backend()` (SIGTERM) to protect postmaster shared memory from cluster crash restarts.
- **SubPlan Elimination, Correlated Scalar Decorrelation & InitPlan Invariants Discipline**: When designing relational queries or ORM models, never embed correlated scalar subqueries in `SELECT` projections or `WHERE` filters (`(SELECT count(*) FROM child WHERE child.fk = parent.id)`). In PostgreSQL execution plans, these generate `SubPlan` nodes that execute repeatedly for every single outer tuple ($100,000\times$), thrashing buffer cache and causing query latency to explode by 100x. Always decorrelate scalar metrics into dedicated Common Table Expressions (`WITH child_agg AS (SELECT fk, count(*) ... GROUP BY fk)`) joined via `LEFT JOIN`, or use window functions to achieve linear single-pass hash execution. Never call non-deterministic volatile functions (`random()`, `clock_timestamp()`, `nextval()`, unannotated UDFs) inside filter subqueries, which silently degrades an $O(1)$ cached `InitPlan 1 (returns $0)` into an $O(N)$ per-row `SubPlan 1`. Prohibit `COUNT(*) > 0` existence checks; always enforce short-circuiting semi-joins via `WHERE EXISTS (SELECT 1 FROM ...)`.
- **Fast-Path Lock Preservation, Lock Table Hash Contention & max_locks_per_transaction Discipline**: In PostgreSQL client code, ORMs, and migrations, strictly respect the 16-relation fast-path lock boundary (`FAST_PATH_BITS_PER_SLOT = 16`). Never permit single transactions to eagerly touch > 16 relations and indexes, which spills locks from backend-local $O(1)$ fast-path arrays into the global shared memory lock table (`LockMethodLockHash`), thrashes the 16 `LockHashPartitionLock` LWLocks, and spikes CPU in kernel spinlocks. On partitioned tables, strictly enforce static partition pruning (`WHERE partition_date = $1`) to prevent queries from locking hundreds of child partitions and thousands of partition indexes, which exhausts postmaster's fixed shared memory allocation and triggers `FATAL: out of shared memory (HINT: You might need to increase max_locks_per_transaction)`. Pre-configure production clusters with `max_locks_per_transaction >= 256`, enforce transaction-scoped `pg_advisory_xact_lock()` to eliminate connection pool lock leaks, and avoid nested ORM savepoints that multiply lock table hash entries.
- **Security Barrier Views, Predicate Pushdown & Leaky Function Side-Channel Invariants Discipline**: When designing views for multi-tenancy, data masking, or row filtering, always declare `WITH (security_barrier = true)`. Never rely on standard views for security boundaries: PostgreSQL's query optimizer will inline standard views and reorder `WHERE` clauses, evaluating user-supplied error-triggering functions or division-by-zero probes on unauthorized rows before security qualifications are evaluated (leaking confidential data via side-channels, CVE-2012-3489). Conversely, recognize that `WITH (security_barrier = true)` blocks predicate pushdown for all non-`LEAKPROOF` operators/functions, turning index seeks into full-table scans. Ensure outer predicates use built-in leakproof operators (`=`, `<`, `>`, `IN`), back base relations with composite indexes `(security_col, filter_col)`, and eliminate inlining optimization barriers (`GROUP BY`, `DISTINCT`, `LIMIT`) within security barrier views. Prefer native Row-Level Security (RLS) on base tables for row isolation, reserving security barrier views strictly for column masking and presentation projections.
- **Synchronous Commit, Replication Quorum Durability Ladders & Group Commit Invariants Discipline**: Never disable `synchronous_commit = off` globally in `postgresql.conf` (which induces unrecoverable data loss and split-brain failover disasters on primary node panics). Instead, enforce strict Differentiated Durability via transaction-scoped `SET LOCAL synchronous_commit`: use `off` for high-throughput batch ingest, logs, and telemetry (bypassing the 1–5ms storage `fsync()` barrier and surging write throughput by 10x–50x while preserving ACID atomicity with $\le 35\text{ms}$ crash loss bounds); use `on` or `local` for double-entry financial ledgers, auth credentials, and idempotency keys; and use `remote_apply` for read-after-write linearizability on read replicas. For HA replication, configure quorum standbys (`synchronous_standby_names = 'ANY M (node1, node2, ...)'`), never fragile `FIRST 1` priority that paralyzes the cluster in `WaitEvent: SyncRep` upon single-node network jitter. On high-concurrency systems, tune group commit (`commit_delay = 20-50µs`, `commit_siblings >= 5`) to coalesce hundreds of concurrent transactions into single physical storage barrier flushes. Never use session-level `SET synchronous_commit` that bleeds across pooled connections.
- **UNLOGGED Tables, Ephemeral Caching, High-Throughput Bulk Staging & Crash Truncation Discipline**: Never query `UNLOGGED` tables on streaming read replicas (`target_session_attrs=read-only`). In PostgreSQL streaming replication, unlogged tables bypass Write-Ahead Logging (WAL) and exist only as empty `_init` forks on standbys, silently returning 0 rows. Route 100% of unlogged queries exclusively to the primary writer node (`target_session_attrs=read-write`). Strictly enforce the Reconstructibility Axiom: only store ephemeral, non-authoritative data in `UNLOGGED` tables (e.g. CSV staging, vector embedding caches, LLM scratchpads), because PostgreSQL's crash recovery mechanism automatically resets the `main` fork of all unlogged tables to 0 rows upon abnormal postmaster termination. Permanently ban dynamic `CREATE TEMP TABLE` in OLTP hot paths to prevent system catalog bloat (`pg_class`, `pg_attribute`) and `shared_inval` queue overflows; use pre-created permanent `UNLOGGED` tables with composite keys `(batch_id UUID, row_index)`. Configure aggressive table-level autovacuum (`autovacuum_vacuum_scale_factor = 0.01, autovacuum_vacuum_threshold = 100`), use atomic `TRUNCATE` (or partition drop) instead of monolithic `DELETE` for batch purges, and never declare `FOREIGN KEY` references between unlogged and logged relations (`SQLSTATE 42809`).
- **Concurrent Index Builds, Invalid Index Recovery & Online Reindexing Swapping Discipline**: Never wrap `CREATE INDEX CONCURRENTLY` (CIC) or `REINDEX CONCURRENTLY` (RC) inside transaction blocks (`BEGIN ... COMMIT`), which crashes with `SQLSTATE 25001`. Configure migration runners with `transactional: false`. When a concurrent build aborts or is canceled, PostgreSQL leaves an invalid index marked `indisvalid = false` but `indisready = true`. This forces every single `INSERT`, `UPDATE`, and `DELETE` to continuously write to an index that the query planner can NEVER use for reads, multiplying write amplification and disk bloat. Always audit schemas for `indisvalid = false` and remediate exclusively via `DROP INDEX CONCURRENTLY IF EXISTS <name>;` (never plain `DROP INDEX`, which grabs an `ACCESS EXCLUSIVE` lock and blocks all production traffic). Before re-running aborted `REINDEX CONCURRENTLY`, inspect and clean orphaned shadow indexes matching `%_ccnew` or `%_ccold` to avoid `relation already exists` errors (`SQLSTATE 42P07`). To eliminate lock convoys during `WaitForOlderSnapshots` phases, enforce `SET lock_timeout = '3000ms'`, and promote unique constraints without write lockouts using the two-step pattern (`CREATE UNIQUE INDEX CONCURRENTLY` followed by `ALTER TABLE ... ADD CONSTRAINT ... UNIQUE USING INDEX`).
- **Free Space Map (FSM), Heap Page Allocation, fillfactor Tuning & RelationExtensionLock Invariants Discipline**: Never leave default `fillfactor = 100` on update-heavy OLTP relations. Default 100% page packing leaves 0% free space for in-place Heap-Only Tuple (HOT) updates, forcing every row modification—even on non-indexed columns—to append a new row version to a different 8KB heap page and write new pointers into every B-Tree, GIN, and GiST index on the table (multiplying write amplification by $5\times–20\times$ and destroying buffer cache hit ratios). Calibrate table-specific `fillfactor = 75–85` on tables with frequent updates, reserving 15–25% headroom for in-place HOT updates. To eliminate `RelationExtensionLock` / `LWLock:RelationExtension` serialization convoys under high-concurrency inserts, vectorize writes using batch unnesting (`UNNEST`) or `COPY`, leverage PostgreSQL 16+ bulk relation extension, and enforce transaction-scoped `SET LOCAL lock_timeout = '2000ms'`. Monitor physical page capacity via `pg_freespace` and assert `n_tup_hot_upd / n_tup_upd >= 0.85`. Never run `VACUUM FULL` or `CLUSTER` to apply fillfactor changes; execute `ALTER TABLE ... SET (fillfactor = X)` followed by online zero-downtime compaction via `pg_repack`.
- **Replication Slots, WAL Retention, max_slot_wal_keep_size & Orphaned Consumer Discipline**: Never set or leave default `max_slot_wal_keep_size = -1` (unlimited) in production PostgreSQL clusters. Default unlimited retention permits a disconnected read replica, crashed CDC consumer (Debezium/Kafka Connect), or orphaned agent test slot to hold `restart_lsn` indefinitely, preventing WAL recycling until the host partition fills to 100% and triggers `PANIC: could not write to log file: No space left on device` (completely shutting down the cluster into an unstartable state). Always enforce `max_slot_wal_keep_size = 50GB` (or $\le 25\%$ available disk capacity) to automatically sacrifice and invalidate runaway slots (`wal_status = 'lost'`) before host storage runs out. Deploy real-time watchdogs auditing `pg_replication_slots` to reap inactive slots (`NOT active` for $> 15\text{m}$), assert byte lag `pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) <= 10GB`, monitor logical slot `age(catalog_xmin) <= 500,000` to prevent system catalog autovacuum freezing and catalog bloat, and on PostgreSQL 17+ HA clusters, always configure logical slots with `failover = true` and `sync_replication_slots = on` to prevent CDC data loss upon primary failover.
- **Autovacuum Cost Limits, Multi-Worker Throttle Division & TID Allocation Discipline**: Never increase `autovacuum_max_workers` (e.g. from 3 to 10) without proportionally scaling `autovacuum_vacuum_cost_limit` from its default 200 to 2500–5000. PostgreSQL divides the global cost limit evenly among all active workers ($C_w = C_{\text{limit}} / N_{\text{active}}$), meaning 10 workers on default settings get only 20 points each, causing workers to sleep 2ms after writing a single 8KB page and dropping throughput below $2\text{ MB/s}$ on high-speed NVMe storage. Never leave `autovacuum_work_mem = -1` (inheriting 64MB `maintenance_work_mem`); explicitly configure dedicated `autovacuum_work_mem = '1024MB'` to guarantee single-pass dead TID collection and prevent disastrous multi-pass index scanning avalanches ($P_{\text{index}} = \lceil N_{\text{dead}} / N_{\text{cap}} \rceil > 1$, which forces repeated full sweeps across all secondary B-tree, GIN, and GiST indexes). Isolate high-churn queue or session tables from the shared cost pool via table-level overrides (`ALTER TABLE ... SET (autovacuum_vacuum_cost_limit = 5000, autovacuum_vacuum_cost_delay = 0)`), enable `log_autovacuum_min_duration = 250`, and audit `age(relfrozenxid) < 100,000,000` to prevent uncancelable emergency anti-wraparound freeze lockouts.
- **Commit Log (CLOG / pg_xact), SLRU Cache Contention & Hint Bit Discipline**: Never expose bulk-loaded tables (`COPY` or batch inserts) immediately to concurrent read queries without first executing `VACUUM (ANALYZE) <relation>` to stamp hint bits (`HEAP_XMIN_COMMITTED`). Reading un-hinted rows forces querying backends to look up transaction commit status in `pg_xact` via the tiny 128-buffer Simple LRU (SLRU) cache, serializing concurrent readers in `WaitEvent: CLogControlLock` or `XactSLRULock`, pegging CPU to 100%, and collapsing query throughput by 95%. When `wal_log_hints = on` (or page checksums are active), setting hint bits dirties shared buffer pages, causing the first `SELECT` query after a checkpoint to emit 8KB Full Page Images (FPIs) into WAL—turning a 50GB read scan into a 50GB WAL write storm that overwhelms disk IOPS and replication lag. Continuously monitor `pg_stat_slru` where `name = 'clog'` (asserting hit ratio $\ge 99\%$), enforce `idle_in_transaction_session_timeout = '15m'` to prevent old transactions from pinning `OldestXmin` and blocking CLOG segment truncation, and strictly ban nested `SAVEPOINT` loops to prevent compounding `pg_subtrans` multi-hop SLRU misses.
- **Visibility Map (VM), All-Visible vs All-Frozen Bits & Vacuum Page-Skipping Discipline**: When designing read-heavy query patterns, always verify that queries intended to be Index-Only Scans (IOS) achieve `Heap Fetches == 0` via `EXPLAIN (ANALYZE, BUFFERS)`. Never scatter un-batched updates across relations without tuning `fillfactor = 80–85` or vertically partitioning volatile columns: row updates clear the Visibility Map's `VISIBILITYMAP_ALL_VISIBLE` bits, degrading low-latency index queries into random disk I/O heap fetches that saturate `shared_buffers`. On high-write relations, proactively calibrate `vacuum_freeze_min_age = 10,000,000` and `vacuum_freeze_table_age = 50,000,000` to ensure routine autovacuum passes stamp `VISIBILITYMAP_ALL_FROZEN` on stable pages; otherwise, subsequent anti-wraparound vacuums cannot skip pages and must sequentially read entire terabyte relations from disk. Disable end-of-vacuum page truncation (`vacuum_truncate = false`) on lock-sensitive OLTP tables to eliminate `ACCESS EXCLUSIVE` lock convoys across heap and VM forks, and deploy `pg_visibility` sentinels (`pg_check_visible`, `pg_check_frozen`) to audit and guarantee zero VM bit corruption.
- **Lock Tree Hierarchy, Head-of-Line Blocking Convoys & Root Blocker Preemption Discipline**: In high-concurrency PostgreSQL workloads, never execute DDL migrations or lock-upgrading operations without configuring transaction-scoped `SET LOCAL lock_timeout = '2000ms'`. Because PostgreSQL's Lock Manager enforces strict FIFO queue order to prevent writer starvation, an un-timed `AccessExclusiveLock` request queuing behind a slow analytical query blocks all subsequent rapid `AccessShareLock` queries (`SELECT`), exhausting connection pools and collapsing database throughput within seconds ($T_{\text{exhaust}} = (c - N_{\text{active}})/\lambda$). Never attempt incident remediation by indiscriminately killing waiting queries (`WHERE wait_event_type = 'Lock'`); this decapitates healthy pooled connections while leaving the blocker alive. Always unwind the lock dependency DAG using recursive traversal over `pg_blocking_pids(pid)` to identify the unique root blocker ($d^+ = 0, d^- > 0$). Execute `pg_cancel_backend(root_pid)` for active runaway queries, and escalate to `pg_terminate_backend(root_pid)` exclusively for leaked connections in `state = 'idle in transaction'`. Enforce server-wide `idle_in_transaction_session_timeout <= 30s` to prevent leaked ORM connections from pinning relation locks indefinitely.
- **Continuous WAL Archiving, `archive_command` vs `archive_library`, Archiver Backpressure & Disk Exhaustion Discipline**: Never configure PostgreSQL continuous archiving (`archive_mode = on/always`) with naive shell-based commands (`cp %p /destination/%f` or direct `aws s3 cp`) without atomic temporary staging (`.tmp` write followed by atomic `rename`) and strict non-overwrite assertion (`test ! -f destination/%f`). Under continuous archiving, PostgreSQL checkpoints can NEVER remove or recycle any WAL segment until the archiver marks it `.done` in `pg_wal/archive_status/` (`XLogArchiveCheckDone()`). If `archive_command` fails due to a network glitch, S3 rate limit, or expired IAM token, the single-threaded archiver process (`pgarch`) retries the same 16MB file indefinitely in an exponential backoff loop without skipping. If write throughput is high, unarchived WAL segments will accumulate until disk space reaches 100%, crashing the postmaster with `PANIC: could not write to file "pg_wal/...": No space left on device` and preventing even crash recovery from starting. In PostgreSQL 15+, always migrate from shell `archive_command` to in-process C `archive_library` (such as pgBackRest) to eliminate the Linux process fork/exec storm and OS PID table saturation (`kernel.pid_max`) under write surges. Never configure aggressive `archive_timeout < 300s` unless sustained write throughput exceeds $16\text{MB} / T_{\text{timeout}}$; otherwise, every timeout forces PostgreSQL to close the segment and pad the remaining space with zeroes, causing 100x WAL volume amplification and ballooning S3 API costs. Deploy real-time sentinels continuously monitoring `pg_stat_archiver` (`failed_count`, `last_failed_time`, `last_failed_wal`) and counting `.ready` backlog files in `pg_wal/archive_status/`, dynamically calculating time to disk exhaustion ($T_{\text{exhaust}} = D_{\text{free}} / \text{Rate}_{\text{wal}}$) to trigger batch ingestion throttling before disk reaches critical thresholds.
- **Logical Replication Conflicts, Subscription Workers, Error Handling, Skip LSN & Origin Tracking Discipline**: In PostgreSQL native logical replication (`CREATE SUBSCRIPTION`), never permit an apply worker to enter an unmonitored crash-loop retry cycle. When an incoming change violates a target constraint (`insert_exists`, `update_missing`, `delete_missing`), the single-threaded apply worker aborts and terminates; postmaster restarts it, and it fetches the exact same LSN, crashing indefinitely and freezing replication across all published tables. While the subscriber crash-loops, the publisher replication slot cannot advance `confirmed_flush_lsn`, hoarding WAL on the primary until disk hits 100% and crashes the publisher with `PANIC: could not write to file "pg_wal/...": No space left on device`. Always configure publisher `max_slot_wal_keep_size = '50GB'` to fence disk space. In PostgreSQL 15+, configure subscriptions with `disable_on_error = true` to cleanly halt the worker rather than burning CPU in a fork-restart loop. In bi-directional (active-active) topologies, strictly enforce PostgreSQL 16+ `origin = none` on subscriptions to prevent applied changes from being republished back in circular infinite loops. Never attempt resolution by dropping and recreating subscriptions (which triggers destructive full table copies) or blindly skipping LSNs without audit trails. Always inspect `pg_stat_subscription_errors` to identify the failing `last_error_lsn`, record a verifiable conflict snapshot, execute surgical `ALTER SUBSCRIPTION <name> SKIP (lsn = '<target_lsn>')`, and re-enable the subscription (`ENABLE`). Guarantee 100% Primary Key or Unique Index coverage on subscriber tables to eliminate catastrophic full sequential scans ($1,600,000\times$ I/O amplification) on incoming updates and deletes.
- **GIN Pending List, FastUpdate Write-Stalls, Inserter Lock Convoys & gin_clean_pending_list Discipline**: Never accept default `fastupdate = on` blindly on write-heavy OLTP relations. Under default settings, GIN indexes append incoming postings to an unindexed heap pending list; once the pending list hits `gin_pending_list_limit` (default 4MB), the backend executing the next `INSERT` or `UPDATE` is hijacked to execute `ginInsertCleanup()` synchronously. This backend acquires an exclusive cleanup lock, reads all pending pages, sorts tens of thousands of postings in memory (or spills to disk if exceeding `work_mem`), and traverses the balanced GIN tree—spiking insertion latency from 0.8ms to 15,000ms. Concurrent writers block on the cleanup lock, collapsing connection pools in $< 2$ seconds, while concurrent readers (`@>`, `@@`) are forced by `ginScanPendingInsert()` to linearly scan every unindexed pending page, degrading read latency by $5,000\times$ and pegging CPU at 100%. For write-heavy relations (> 100 writes/sec or requiring deterministic p99 write latency $< 15\text{ms}$), explicitly declare `CREATE INDEX ... WITH (fastupdate = off)`. If `fastupdate = on` is retained for read-heavy or batch-loaded tables, reduce `gin_pending_list_limit` to `512kB`–`1024kB` to bound inline stalls to $< 40\text{ms}$, and deploy scheduled out-of-band background workers invoking `SELECT gin_clean_pending_list(index_oid)` under non-blocking transaction-scoped advisory locks with strict `lock_timeout = '2000ms'` and `statement_timeout = '30000ms'`.
- **Hash Indexes, Crash-Safe WAL Logging, Dynamic Bucket Splitting & Overflow Page Chain Discipline**: Since PostgreSQL 10, Hash indexes (`CREATE INDEX ... USING hash (col)`) are fully crash-safe, WAL-logged, and replicable to streaming standbys. For large string or token columns (URLs, SHA-256 hashes, UUIDs $\ge 32\text{ bytes}$) queried exclusively via `=` equality, Hash indexes consume constant 10 bytes per tuple regardless of key size, providing 60%–80% storage reduction and fitting completely in `shared_buffers` compared to bloat-prone B-Trees. However, strictly enforce the 3 Architectural Hash Index Boundaries: (1) **Uniqueness Prohibition**: Never attempt `CREATE UNIQUE INDEX ... USING hash` or back `PRIMARY KEY` or `FOREIGN KEY` references with Hash indexes (`SQLSTATE 0A000: access method "hash" does not support unique indexes`). (2) **Single-Column Sargability**: Hash indexes only support single-column indexing and strictly support ONLY `=` equality lookups. Querying hash-indexed columns with `<`, `>`, `<=`, `>=`, `BETWEEN`, or `ORDER BY` is non-sargable, forcing PostgreSQL into 100% full sequential table scans (`Seq Scan`). (3) **Overflow Chain Degradation**: Deploy `pageinspect` or `relpages` sentinels auditing overflow page ratio ($N_{\text{overflow}} / N_{\text{total}} \le 15\%$). When skewed data or high write volume causes deep overflow chains, point lookups degrade into $O(K)$ sequential page traversals; remediate with online `REINDEX INDEX CONCURRENTLY` under non-blocking advisory locks.
- **Large Objects (LOBs / BLOBs), pg_largeobject Catalog Bloat, lo_unlink Orphan Leaks & Chunked Streaming Discipline**: Never use naked `OID` columns to store Large Objects without attaching automatic unlinking triggers (`BEFORE UPDATE OF lob_oid OR DELETE ... PERFORM lo_unlink(OLD.lob_oid);`). In PostgreSQL, relational `DELETE` drops the row containing the OID pointer but leaves the underlying 2KB binary chunks in `pg_largeobject` forever, rapidly bloating system catalogs into hundreds of gigabytes and exhausting disk space. Strictly enforce the 3-Zone Storage Sizing Boundary: use `bytea` with LZ4 compression for payloads $\le 256\text{KB}$; transaction-scoped Large Objects with streaming for $256\text{KB} < \text{Size} \le 5\text{MB}$; and S3-compatible Object Storage (S3 / R2 / MinIO) with presigned URLs for all files $> 5\text{MB}$ (eliminating $2\times–4\times$ WAL amplification and multi-hour PITR restore delays). Never execute unthrottled `vacuumlo` or monolithic unlinking loops; execute orphan purging in discrete keyset batches ($\le 500$) under non-blocking advisory locks (`pg_try_advisory_lock`) with `lock_timeout <= 2000ms`. Always wrap Large Object read/write streams inside explicit transactions, and never assume PostgreSQL native logical replication replicates `pg_largeobject` to subscribers.
