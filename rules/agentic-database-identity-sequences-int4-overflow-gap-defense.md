## 2. Mathematical Formalism: Exhaustion Sizing, Lock Contention Differential & Sequence WAL Reduction

### 2.1 Integer Exhaustion Time-to-Failure Calculus
Let $V_{\max}$ be the maximum representable value of the column data type ($V_{\max} = 2^{31}-1 = 2,147,483,647$ for signed 32-bit `int4`; $V_{\max} = 2^{63}-1 \approx 9.22 \times 10^{18}$ for signed 64-bit `int8`). Let $V_{\text{curr}}$ be the current sequence value, and $\lambda$ be the average sustained row insertion rate (writes per second).

The time to catastrophic exhaustion $T_{\text{exhaust}}$ is:

$$T_{\text{exhaust}} = \frac{V_{\max} - V_{\text{curr}}}{\lambda}$$

**Production Case Study**: A payments or webhook table receiving a moderate load of $\lambda = 350\text{ inserts/sec}$:

$$T_{\text{exhaust}} = \frac{2,147,483,647 - 0}{350 \times 86,400\text{ sec/day}} \approx 71.0\text{ days}$$

Without proactive monitoring, a fast-growing system built on 32-bit `SERIAL` will suffer an unrecoverable write stoppage within two and a half months of launch. Under `BIGINT`:

$$T_{\text{exhaust\_bigint}} = \frac{9.22 \times 10^{18}}{350 \times 86,400 \times 365.25} \approx 8.35 \times 10^8\text{ years}$$

### 2.2 Lock Contention Differential: Synchronous Rewrite vs 4-Phase Zero-Downtime Migration
When executing a naive synchronous type conversion:

$$\text{ALTER TABLE } T \text{ ALTER COLUMN id TYPE bigint;}$$

PostgreSQL acquires `ACCESS EXCLUSIVE` lock on $T$, which blocks **all** concurrent queries (reads and writes). The engine reads every tuple from the physical heap, converts the 4-byte integer to an 8-byte integer, writes a brand-new table heap file, and reconstructs all indexes.

Let $S_{\text{table}}$ be the size of the table on disk, and $R_{\text{disk\_seq\_write}}$ be the sequential I/O write throughput of the database storage. The lock hold time $t_{\text{lock\_sync}}$ is:

$$t_{\text{lock\_sync}} \approx \frac{S_{\text{table}}}{R_{\text{disk\_seq\_write}}} + \sum_{i=1}^M \frac{S_{\text{idx}_i}}{R_{\text{index\_build}}}$$

Under incoming query arrival rate $\lambda_{\text{traffic}}$, the queue of blocked connections $Q_{\text{blocked}}$ builds up according to Little's Law:

$$Q_{\text{blocked}} = \lambda_{\text{traffic}} \times t_{\text{lock\_sync}}$$

For a 200GB table on an NVMe storage subsystem writing at $250\text{ MB/s}$ ($t_{\text{lock\_sync}} \approx 800\text{ s} \approx 13.3\text{ minutes}$) under $\lambda_{\text{traffic}} = 500\text{ queries/sec}$:

$$Q_{\text{blocked}} = 500 \times 800 = 400,000\text{ queries}$$

Since typical database connection pools allow $N_{\text{pool}} \approx 100–500$ connections, connection pools are exhausted within **$200\text{ milliseconds}$**, causing total upstream gateway timeouts ($504$ Cascades) and server out-of-memory crashes.

Conversely, under the **4-Phase Zero-Downtime Migration Protocol**:
- Phase 1 (Add Column): Instant metadata-only operation ($t_{\text{lock}} < 2\text{ms}$).
- Phase 2 (Install Sync Trigger): Minimal metadata lock ($t_{\text{lock}} < 5\text{ms}$).
- Phase 3 (Bounded Batch Backfill): Zero exclusive table locks; updates execute in micro-transactions of $\le 2000$ rows.
- Phase 4 (Concurrent Index Build & Column Swap): Index built concurrently with zero read/write blocking; final swap executes inside a transaction protected by `SET lock_timeout = '2s'` ($t_{\text{lock}} < 10\text{ms}$).

Total blocked query queue under zero-downtime migration:

$$Q_{\text{blocked\_phased}} = \lambda_{\text{traffic}} \times \max(t_{\text{lock}}) = 500 \times 0.01\text{ s} \le 5\text{ queries}$$

### 2.3 Sequence Buffer Contention & WAL Amplification Model
PostgreSQL sequences maintain their current state in a dedicated single-page buffer in shared memory. Under `CACHE = 1`, each worker transaction invoking `nextval()` must:
1. Acquire an exclusive lightweight latch (`LWLock`) on the sequence buffer page.
2. Advance `last_value = last_value + log_cnt`.
3. Emit a Write-Ahead Log (WAL) record describing the sequence advance.
4. Release the sequence latch.

When $W$ concurrent workers execute `INSERT` statements simultaneously, sequence latch acquisition forms a serial bottleneck. Let $C$ be the sequence cache size. The number of sequence WAL records generated for $N$ total rows is:

$$W_{\text{wal\_seq}}(C) = \left\lceil \frac{N}{C} \right\rceil$$

For $N = 10,000,000$ rows with default $C = 1$:
$$W_{\text{wal\_seq}}(1) = 10,000,000\text{ WAL records}$$

With production-tuned $C = 100$:
$$W_{\text{wal\_seq}}(100) = 100,000\text{ WAL records} \quad (99.0\%\text{ reduction in sequence WAL I/O})$$

## 3. The 5 Core Production Invariants

### 3.1 Invariant 1: Mandatory 64-Bit BIGINT Storage Invariant
- **Rule**: Every auto-increment surrogate primary key and foreign key referencing it MUST be declared as signed 64-bit `BIGINT` (`int8`).
- **Prohibition**: Autonomous agents are STRICTLY PROHIBITED from using `SERIAL`, `INT4`, `INTEGER`, or unsigned 32-bit integer types for primary keys or append-only transactional tables.
- **Client JSON Boundary Defense**: Relational `BIGINT` ($2^{63}-1$) exceeds JavaScript's `Number.MAX_SAFE_INTEGER` ($2^{53}-1 = 9,007,199,254,740,991$). All API serialization layers (REST JSON, GraphQL, gRPC) MUST serialize `int8` primary keys as strings (`string`) or dedicated `BigInt` scalar types to prevent client-side silent numerical truncation.

### 3.2 Invariant 2: Modern SQL:2003 `GENERATED ALWAYS AS IDENTITY`
- **Rule**: Replace deprecated PostgreSQL `SERIAL` / `BIGSERIAL` with ANSI SQL:2003 standard `IDENTITY` columns.
- **Enforcement**:
  - Use `GENERATED ALWAYS AS IDENTITY` for system-owned primary keys where client code should NEVER supply its own ID values.
  - Use `GENERATED BY DEFAULT AS IDENTITY` only when external data import or offline migration requires explicitly specified ID overrides.
- **Sequence Ownership**: Identity sequences are formally owned by the table column in `pg_depend`. When the column or table is dropped, the sequence is automatically dropped with zero orphaned objects.

```sql
-- ✅ PRODUCTION STANDARD: SQL:2003 Identity Definition
CREATE TABLE customers (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email VARCHAR(255) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);
```

### 3.3 Invariant 3: Four-Phase Zero-Downtime `int4` to `BIGINT` Live Migration
When an existing production table approaches 32-bit `int4` exhaustion, autonomous agents MUST NOT run synchronous `ALTER COLUMN TYPE`. Instead, follow the strict 4-phase Expand-Contract zero-downtime protocol:

```sql
-- ============================================================================
-- PHASE 1: EXPAND - Add Shadow BIGINT Column (Instant Metadata Operation)
-- ============================================================================
ALTER TABLE orders ADD COLUMN id_bigint BIGINT;

-- ============================================================================
-- PHASE 2: DUAL-WRITE - Install Synchronization Trigger for In-Flight Writes
-- ============================================================================
CREATE OR REPLACE FUNCTION trg_sync_orders_id_bigint()
RETURNS TRIGGER AS $$
BEGIN
  NEW.id_bigint := NEW.id;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_id_bigint_sync
BEFORE INSERT ON orders
FOR EACH ROW
EXECUTE FUNCTION trg_sync_orders_id_bigint();

-- ============================================================================
-- PHASE 3: BACKFILL - Bounded Chunked Backfill with Replica Lag Throttling
-- Execute via background worker in small batches (e.g., LIMIT 2000)
-- ============================================================================
-- UPDATE orders SET id_bigint = id WHERE id_bigint IS NULL AND id >= $1 AND id < $2;

-- Build unique index concurrently without blocking writes
CREATE UNIQUE INDEX CONCURRENTLY idx_orders_id_bigint_unique ON orders (id_bigint);

-- ============================================================================
-- PHASE 4: CONTRACT - Atomic Column Swap & Constraint Handover
-- ============================================================================
BEGIN;
SET LOCAL lock_timeout = '2s';

-- 1. Drop dual-write trigger
DROP TRIGGER orders_id_bigint_sync ON orders;
DROP FUNCTION trg_sync_orders_id_bigint();

-- 2. Promote id_bigint to NOT NULL
ALTER TABLE orders ALTER COLUMN id_bigint SET NOT NULL;

-- 3. Swap columns
ALTER TABLE orders RENAME COLUMN id TO id_legacy_int4;
ALTER TABLE orders RENAME COLUMN id_bigint TO id;

-- 4. Re-bind sequence ownership to the new BIGINT column
ALTER SEQUENCE orders_id_seq OWNED BY orders.id;
ALTER TABLE orders ALTER COLUMN id SET DEFAULT nextval('orders_id_seq');

-- 5. Swap Primary Key Constraint using existing concurrent unique index
ALTER TABLE orders DROP CONSTRAINT orders_pkey;
ALTER TABLE orders ADD CONSTRAINT orders_pkey PRIMARY KEY USING INDEX idx_orders_id_bigint_unique;

COMMIT;
```

### 3.4 Invariant 4: High-Concurrency Sequence Pre-Allocation (`CACHE 50–100`)
- **Rule**: On high-throughput transactional tables ($>1,000\text{ inserts/sec}$), sequences MUST be configured with a cache size of at least `CACHE 50` or `CACHE 100`.
- **Concurrency Benefit**: Worker sessions pre-allocate batches of sequence numbers in session-local memory, eliminating `LWLock` buffer contention on the shared sequence page and drastically reducing WAL generation.
- **Trade-off Awareness**: If a database session disconnects or crashes, remaining cached sequence numbers allocated to that session are discarded. Applications must accept sequence gaps (see Invariant 5).

```sql
-- Tune existing sequence for high concurrency
ALTER SEQUENCE orders_id_seq CACHE 100;
```

### 3.5 Invariant 5: Statutory Gapless Accounting Invariant vs Surrogate Sequences
- **Rule**: Non-transactional database sequences MUST NEVER be used for statutory gapless financial audit trails (e.g., invoice numbers, legal receipt numbers).
- **The Gap Mechanism**: Database sequences operate outside transaction boundaries. When a transaction rolls back or fails, sequence numbers consumed by `nextval()` are permanently burnt and NEVER restored.
- **Production Standard**:
  - Keep surrogate primary keys (`id BIGINT`) separate from business document numbers.
  - Statutory contiguous invoice numbers MUST be generated using an explicit pessimistic row lock table (`SELECT counter FROM invoice_series WHERE series = $1 FOR UPDATE`) within the exact business transaction, or via an outbox event processor.

```sql
-- Statutory Contiguous Invoice Sequence Pattern
CREATE TABLE invoice_series (
  series_name VARCHAR(32) PRIMARY KEY,
  current_counter BIGINT NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp()
);

-- Transactional Contiguous Counter Increment
BEGIN;
SELECT current_counter + 1
FROM invoice_series
WHERE series_name = '2026-US-INV'
FOR UPDATE;

-- Insert invoice using exact sequential counter
INSERT INTO invoices (id, invoice_number, amount_cents)
VALUES (
  DEFAULT, -- Handled by BIGINT sequence
  'INV-2026-' || LPAD((SELECT current_counter FROM invoice_series WHERE series_name = '2026-US-INV')::TEXT, 8, '0'),
  19900
);

UPDATE invoice_series
SET current_counter = current_counter + 1, updated_at = clock_timestamp()
WHERE series_name = '2026-US-INV';
COMMIT;
```

## 4. Production Reference Implementation: TypeScript & SQL

Below is the complete, production-grade `AgenticDatabaseSequenceEngine` in TypeScript, providing automated sequence capacity auditing, time-to-exhaustion projections, and zero-downtime migration generation:

```typescript
import { Pool, PoolClient } from 'pg';

export interface SequenceAuditResult {
  schemaName: string;
  tableName: string;
  columnName: string;
  dataType: string;
  sequenceName: string;
  currentValue: bigint;
  maxValue: bigint;
  percentConsumed: number;
  isCycle: boolean;
  cacheSize: number;
  status: 'HEALTHY' | 'WARNING_75' | 'CRITICAL_90' | 'OVERFLOW_EMERGENCY';
  estimatedDaysToExhaustion?: number;
}

export class AgenticDatabaseSequenceEngine {
  constructor(private readonly pool: Pool) {}

  /**
   * Audits all database sequences and identity columns for 32-bit int4 exhaustion,
   * cache contention risk, and CYCLE vulnerability.
   */
  async auditSequences(dailyInsertRateEstimate: number = 100_000): Promise<SequenceAuditResult[]> {
    const client = await this.pool.connect();
    try {
      const sql = `
        SELECT
          ns.nspname AS schema_name,
          tbl.relname AS table_name,
          att.attname AS column_name,
          typ.typname AS data_type,
          seq_ns.nspname || '.' || seq.relname AS sequence_name,
          s.last_value,
          s.max_value,
          s.is_cycled,
          s.cache_size
        FROM pg_class seq
        JOIN pg_namespace seq_ns ON seq.relnamespace = seq_ns.oid
        JOIN pg_sequences s ON s.schemaname = seq_ns.nspname AND s.sequencename = seq.relname
        JOIN pg_depend dep ON dep.objid = seq.oid AND dep.deptype IN ('a', 'i')
        JOIN pg_class tbl ON dep.refobjid = tbl.oid
        JOIN pg_namespace ns ON tbl.relnamespace = ns.oid
        JOIN pg_attribute att ON att.attrelid = tbl.oid AND att.attnum = dep.refobjsubid
        JOIN pg_type typ ON att.atttypid = typ.oid
        WHERE seq.relkind = 'S'
          AND ns.nspname NOT IN ('pg_catalog', 'information_schema')
        ORDER BY (s.last_value::numeric / s.max_value::numeric) DESC;
      `;

      const res = await client.query(sql);
      const results: SequenceAuditResult[] = [];

      for (const row of res.rows) {
        const curr = BigInt(row.last_value || 0);
        const maxVal = BigInt(row.max_value);
        const percent = Number((curr * 10000n) / maxVal) / 100;

        let status: SequenceAuditResult['status'] = 'HEALTHY';
        if (percent >= 99.0) {
          status = 'OVERFLOW_EMERGENCY';
        } else if (percent >= 90.0) {
          status = 'CRITICAL_90';
        } else if (percent >= 75.0) {
          status = 'WARNING_75';
        }

        // Calculate time to exhaustion
        let daysToExhaust: number | undefined;
        if (dailyInsertRateEstimate > 0) {
          const remaining = maxVal - curr;
          daysToExhaust = Math.max(0, Number(remaining / BigInt(dailyInsertRateEstimate)));
        }

        results.push({
          schemaName: row.schema_name,
          tableName: row.table_name,
          columnName: row.column_name,
          dataType: row.data_type,
          sequenceName: row.sequence_name,
          currentValue: curr,
          maxValue: maxVal,
          percentConsumed: percent,
          isCycle: Boolean(row.is_cycled),
          cacheSize: Number(row.cache_size || 1),
          status,
          estimatedDaysToExhaustion: daysToExhaust,
        });
      }

      return results;
    } finally {
      client.release();
    }
  }

  /**
   * Generates production-grade, zero-downtime expand-contract migration SQL
   * to convert a vulnerable int4 sequence/identity column to BIGINT.
   */
  generateZeroDowntimeBigintMigration(
    tableName: string,
    columnName: string,
    sequenceName: string
  ): {
    phase1Expand: string;
    phase2SyncTrigger: string;
    phase3BackfillChunk: string;
    phase4Swap: string;
  } {
    const shadowCol = `${columnName}_bigint`;
    const triggerFn = `trg_sync_${tableName}_${shadowCol}`;
    const triggerName = `trg_${tableName}_${shadowCol}_sync`;
    const tempIndex = `idx_${tableName}_${shadowCol}_unique`;

    return {
      phase1Expand: `
        -- Step 1: Add shadow BIGINT column (instant metadata change)
        ALTER TABLE ${tableName} ADD COLUMN ${shadowCol} BIGINT;
      `,
      phase2SyncTrigger: `
        -- Step 2: Ensure all in-flight inserts populate the shadow column
        CREATE OR REPLACE FUNCTION ${triggerFn}()
        RETURNS TRIGGER AS $$
        BEGIN
          NEW.${shadowCol} := NEW.${columnName};
          RETURN NEW;
        END;
        $$ LANGUAGE plpgsql;

        CREATE TRIGGER ${triggerName}
        BEFORE INSERT ON ${tableName}
        FOR EACH ROW
        EXECUTE FUNCTION ${triggerFn}();
      `,
      phase3BackfillChunk: `
        -- Step 3: Backfill historical rows in chunks (run iteratively via background job)
        -- Throttled with LIMIT 2000 and replica lag checks
        UPDATE ${tableName}
        SET ${shadowCol} = ${columnName}
        WHERE ${shadowCol} IS NULL
          AND ${columnName} >= $1 AND ${columnName} < $2;

        -- Create unique index CONCURRENTLY outside transaction
        CREATE UNIQUE INDEX CONCURRENTLY ${tempIndex} ON ${tableName} (${shadowCol});
      `,
      phase4Swap: `
        -- Step 4: Atomic cutover protected by sub-second lock_timeout
        BEGIN;
        SET LOCAL lock_timeout = '2s';

        DROP TRIGGER ${triggerName} ON ${tableName};
        DROP FUNCTION ${triggerFn}();

        ALTER TABLE ${tableName} ALTER COLUMN ${shadowCol} SET NOT NULL;
        ALTER TABLE ${tableName} RENAME COLUMN ${columnName} TO ${columnName}_legacy_int4;
        ALTER TABLE ${tableName} RENAME COLUMN ${shadowCol} TO ${columnName};

        -- Re-associate sequence and update default
        ALTER SEQUENCE ${sequenceName} OWNED BY ${tableName}.${columnName};
        ALTER SEQUENCE ${sequenceName} CACHE 50;
        ALTER TABLE ${tableName} ALTER COLUMN ${columnName} SET DEFAULT nextval('${sequenceName}');

        -- Swap Primary Key constraint using pre-built concurrent unique index
        ALTER TABLE ${tableName} DROP CONSTRAINT ${tableName}_pkey;
        ALTER TABLE ${tableName} ADD CONSTRAINT ${tableName}_pkey PRIMARY KEY USING INDEX ${tempIndex};

        COMMIT;
      `,
    };
  }
}
```

## 6. Machine-Verifiable Definition of Done (DoD)

Before any schema migration, primary key modification, or sequence configuration change is merged into production, autonomous agents MUST verify all 6 criteria:

- [ ] **Gate 1: Zero 32-Bit Integer Auto-Increment Primary Keys**: All newly created tables define surrogate auto-increment primary keys as `BIGINT` (`int8`) or use RFC 9562 UUIDv7. Not a single instance of `id SERIAL` or `id INT GENERATED` exists in PR migrations.
- [ ] **Gate 2: Modern ANSI SQL:2003 `IDENTITY` Standard**: Identity columns declare `GENERATED ALWAYS AS IDENTITY` or `GENERATED BY DEFAULT AS IDENTITY`. Deprecated `SERIAL` pseudo-types are rejected by database linters.
- [ ] **Gate 3: Explicit `NO CYCLE` & High-Concurrency `CACHE` Tuning**: All sequence definitions specify `NO CYCLE`. High-throughput tables ($>1000\text{ writes/sec}$) set `CACHE 50` or `CACHE 100` to amortize sequence buffer latches.
