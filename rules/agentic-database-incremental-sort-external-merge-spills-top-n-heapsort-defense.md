## 1. Architectural Taxonomy: The 6 Sorting Catastrophes vs The 5-Tier Governance Ladder

In PostgreSQL, sorting operations generated by `ORDER BY`, `DISTINCT`, `UNION`, `WINDOW`, or presorted input requirements for `Merge Join` and `GroupAggregate` are executed through four distinct algorithmic strategies:
1. **Top-N Heapsort (`Sort Method: top-N heapsort`)**:
   - Used when a query requests bounded ordering via `ORDER BY ... LIMIT K` (with small $K$, typically $K \le 10,000$).
   - The executor allocates a bounded priority heap of size $K$ in memory.
   - For each input tuple, if the heap is not full, it is inserted in $O(\log K)$ time. Once full, new tuples are compared against the current worst element; if better, the worst is evicted and the new tuple inserted in $O(\log K)$ time.
   - Total memory is strictly $O(K)$ bounded, and total time complexity is $O(N \log K)$.
2. **Quicksort (`Sort Method: quicksort`)**:
   - Used when all input tuples fit comfortably within the allocated memory budget (`work_mem`).
   - The executor loads all pointers and sort keys into a contiguous memory buffer and performs an in-memory quicksort or introsort.
   - Space complexity is $O(N)$ memory, and time complexity is $O(N \log N)$ CPU operations.
3. **External Merge Sort (`Sort Method: external merge Disk`)**:
   - Triggered when the memory required to sort the input relation exceeds `work_mem`.
   - The executor builds sorted runs in memory up to `work_mem`, flushes each sorted run to temporary disk files (`pgsql_tmp`), and executes a multi-pass external $k$-way merge across the runs.
   - Generates massive physical I/O (`temp_blks_written` and `temp_blks_read`), saturates NVMe controllers, evicts hot pages from OS page cache, and inflates query latency by 50x–200x.
4. **Incremental Sort (`Incremental Sort`)**:
   - Introduced in PostgreSQL 13 (`enable_incremental_sort = on`).
   - Exploits partial pre-sorting: when data is already ordered by a prefix of the requested sort keys (e.g. from an existing B-Tree index on `(tenant_id, created_at)` and the query requests `ORDER BY tenant_id, created_at, status`).
   - Instead of sorting the entire multi-million row table, the executor reads rows grouped by the prefix keys and sorts each group individually in memory by the remaining keys (`Full-sort Groups` and `Pre-sorted Groups`).
   - Reduces peak memory from $O(N)$ to $O(\max |G_{\text{prefix}}|)$, enables early pipeline streaming, and drops latency by 80%–99%.

## 2. Mathematical & Algorithmic Foundations

### 2.1 Sort Memory Footprint Model (Quicksort & Tuplesort)

Let $N$ be the number of rows to be sorted, $S_{\text{tuple}}$ be the average byte width of a serialized tuple including datum pointers, and $S_{\text{ptr}}$ be the sort pointer array slot overhead ($S_{\text{ptr}} = 8 \text{ bytes}$ on 64-bit architectures, plus $8 \text{ bytes}$ for leading sort key abbreviation).

The physical memory $M_{\text{quicksort}}(N)$ required to perform an in-memory Tuplesort without spilling to disk is:

$$M_{\text{quicksort}}(N) = N \times \left( S_{\text{tuple}} + S_{\text{ptr}} + S_{\text{tuple\_overhead}} \right) + S_{\text{memcontext}}$$

Where:
- $S_{\text{tuple\_overhead}} = 24 \text{ bytes}$ (PostgreSQL `SortTuple` struct containing tuple pointer, first datum value, and null flag).
- $S_{\text{memcontext}} = 8192 \text{ bytes}$ (standard `AllocSet` block header overhead).

The fundamental invariant for **Zero-Spill In-Memory Sorting** is:

$$M_{\text{quicksort}}(N) \le \text{work\_mem} \times 1024 \text{ bytes}$$

If $M_{\text{quicksort}}(N) > \text{work\_mem} \times 1024$, PostgreSQL triggers an **External Merge Sort**:
- The executor creates initial sorted runs in memory up to `work_mem`.
- Each run is written to temporary files in `pgsql_tmp`.
- If the number of runs $R = \lceil M_{\text{quicksort}}(N) / \text{work\_mem} \rceil$ exceeds the fan-in merge capacity (typically bounded by available file descriptors and tape buffers), multi-pass merge sorting is performed:

$$\text{Passes} = \left\lceil \log_{\text{fan\_in}} (R) \right\rceil$$

Total disk write volume generated by external merge sort is:

$$V_{\text{spill\_bytes}} = 2 \times N \times S_{\text{tuple}} \times \text{Passes}$$

On an uncalibrated default `work_mem = 4MB` instance sorting 10,000,000 rows ($S_{\text{tuple}} = 120 \text{ bytes}$):
- Total data size: $1.2 \text{ GB}$.
- Number of runs: $R \approx 300$.
- With a fan-in of 32, $\text{Passes} = 2$.
- Total temporary disk I/O: $V_{\text{spill\_bytes}} \approx 2 \times 1.2 \text{ GB} \times 2 = 4.8 \text{ GB}$ of disk reads and writes, freezing NVMe storage pipelines and spiking query duration from 40ms to 42,000ms.

### 2.2 Top-N Heapsort Bounded Memory Model

For queries with `ORDER BY ... LIMIT K`, when the planner recognizes that only the top $K$ tuples are required and no window functions or blocking barriers intervene, it selects **Top-N Heapsort**:

$$M_{\text{topn}}(K) = K \times \left( S_{\text{tuple}} + S_{\text{ptr}} + S_{\text{tuple\_overhead}} \right) = \mathcal{O}(K)$$

Regardless of whether the input relation has $10^5$ or $10^9$ rows ($N \gg K$), memory usage is strictly bounded by $K$.

Time complexity comparison:
- **Full Quicksort**: $T(N) = \mathcal{O}(N \log N)$
- **External Merge Sort**: $T(N) = \mathcal{O}(N \log N) + \mathcal{O}\left( \frac{N \times S_{\text{tuple}}}{\text{Disk\_Throughput}} \right)$
- **Top-N Heapsort**: $T(N, K) = \mathcal{O}(N \log K)$

When $N = 1,000,000$ and $K = 50$:
- Quicksort comparisons: $10^6 \times \log_2(10^6) \approx 20,000,000$ comparisons.
- Top-N Heapsort comparisons: $10^6 \times \log_2(50) \approx 5,640,000$ comparisons ($3.5\times$ fewer comparisons).
- Memory reduction: from $150 \text{ MB}$ to $8 \text{ KB}$ ($18,750\times$ memory savings), completely immunizing against disk spills.

### 2.3 Incremental Sort Bounded Group Model

When an existing B-Tree index provides ordering on a prefix key set $\mathbf{P} = \{P_1, \dots, P_m\}$, and the query requests ordering on $\mathbf{P} \cup \mathbf{S}$ where $\mathbf{S} = \{S_1, \dots, S_n\}$:

Instead of sorting the entire table of $N$ rows, `Incremental Sort` partitions incoming tuples into contiguous groups $G_1, G_2, \dots, G_m$ where all tuples in $G_i$ share identical values for $\mathbf{P}$.

Memory required for Incremental Sort is bounded by the **maximum cardinality of a single prefix group**:

$$M_{\text{inc\_sort}} = \max_{i} |G_i| \times \left( S_{\text{tuple}} + S_{\text{overhead}} \right) \ll M_{\text{full}}(N)$$

Speedup theorem for Incremental Sort with early termination `LIMIT K`:

$$\mathcal{S}_{\text{inc\_sort}} \approx \frac{N}{|G_1| + \dots + |G_k|} \quad \text{where } \sum_{i=1}^k |G_i| \ge K$$

If $N = 10,000,000$ and each prefix group contains 100 rows, returning $K = 20$ rows requires sorting only a single group of 100 rows rather than $10,000,000$ rows:

$$\mathcal{S}_{\text{inc\_sort}} \approx \frac{10,000,000}{100} = 100,000\times \text{ latency improvement}$$

### 2.4 Collation Binary Comparison Speedup Calculus

In PostgreSQL, sorting text columns under standard locales (`en_US.UTF-8` or default ICU collations) requires invoking the libc/ICU collation function `strcoll()` on every comparison.

Let $T_{\text{strcoll}}$ be the time to execute a locale-aware collation comparison (decoding UTF-8 code points, weight lookup, contraction handling), and $T_{\text{memcmp}}$ be the time to execute a direct byte comparison under `COLLATE "C"`:

$$T_{\text{strcoll}} \approx 45 \text{ ns to } 120 \text{ ns per comparison}$$
$$T_{\text{memcmp}} \approx 2 \text{ ns to } 5 \text{ ns per comparison}$$

The collation acceleration factor $\mathcal{A}_{\text{collate}}$ is:

$$\mathcal{A}_{\text{collate}} = \frac{T_{\text{strcoll}}}{T_{\text{memcmp}}} \approx 10\times - 25\times$$

For a sort of $1,000,000$ strings, switching to `COLLATE "C"` (or `COLLATE "C.UTF-8"`) reduces CPU comparison time from $2.4 \text{ seconds}$ to $80 \text{ ms}$.

## 3. Concrete Implementation: TypeScript `AgenticSortGuardEngine`

Below is the production-grade TypeScript guard engine for inspecting `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` execution plans, detecting external merge sort spills, verifying Top-N Heapsort preservation, auditing Incremental Sort group performance, and generating transaction-scoped remediation SQL.

```typescript
// agentic-sort-guard-engine.ts
// Autonomous Plan Auditor & GUC Governor for PostgreSQL Sorting & Incremental Sort

export interface SortPlanViolation {
  nodeType: 'Sort' | 'Incremental Sort' | 'Gather Merge';
  severity: 'CRITICAL' | 'WARNING' | 'INFO';
  issue: string;
  remedy: string;
  recommendedGucSql?: string;
  recommendedIndexSql?: string;
  metrics: {
    sortMethod?: string;
    sortSpaceType?: string;
    sortSpaceUsedKb?: number;
    actualRows?: number;
    planRows?: number;
    presortedKey?: string;
    fullSortGroups?: number;
    presortedGroups?: number;
    workersAllocated?: number;
  };
}

export interface SortAuditReport {
  isCompliant: boolean;
  hasDiskSpill: boolean;
  isTopNPreserved: boolean;
  hasIncrementalSort: boolean;
  hasLocaleCollationPenalty: boolean;
  violations: SortPlanViolation[];
  suggestedWorkMemMB: number;
}

export class AgenticSortGuardEngine {
  private readonly defaultWorkMemMB: number;
  private readonly maxWorkMemCeilingMB: number;

  constructor(defaultWorkMemMB: number = 4, maxWorkMemCeilingMB: number = 256) {
    this.defaultWorkMemMB = defaultWorkMemMB;
    this.maxWorkMemCeilingMB = maxWorkMemCeilingMB;
  }

  /**
   * Evaluates EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) execution trees for sort anomalies.
   */
  public auditPlan(explainJson: string, querySQL?: string): SortAuditReport {
    let parsed: any;
    try {
      parsed = JSON.parse(explainJson);
    } catch {
      throw new Error('AgenticSortGuardEngine: Invalid EXPLAIN JSON input.');
    }

    const rootPlan = Array.isArray(parsed) ? parsed[0]?.Plan : parsed?.Plan;
    if (!rootPlan) {
      throw new Error('AgenticSortGuardEngine: Missing root Plan node.');
    }

    const violations: SortPlanViolation[] = [];
    let hasDiskSpill = false;
    let isTopNPreserved = false;
    let hasIncrementalSort = false;
    let hasLocaleCollationPenalty = false;
    let maxSortSpaceUsedKb = 0;

    const queryHasLimit = querySQL ? /\bLIMIT\s+\d+\b/i.test(querySQL) : false;
    const queryHasLocaleSort = querySQL ? /\bORDER\s+BY\b/i.test(querySQL) && !/COLLATE\s+"C"/i.test(querySQL) : false;

    const traverse = (node: any, parentNode: any | null) => {
      const nodeType = node['Node Type'] ?? '';
      const actualRows = node['Actual Rows'] ?? 0;
      const planRows = node['Plan Rows'] ?? 0;

      // 1. Audit Standard Sort Nodes
      if (nodeType === 'Sort') {
        const sortMethod = node['Sort Method'] ?? '';
        const sortSpaceType = node['Sort Space Type'] ?? '';
        const sortSpaceUsedKb = node['Sort Space Used'] ?? 0;

        if (sortSpaceUsedKb > maxSortSpaceUsedKb) {
          maxSortSpaceUsedKb = sortSpaceUsedKb;
        }

        // Check for External Merge Sort Disk Spill
        if (sortSpaceType === 'Disk' || sortMethod.includes('external merge')) {
          hasDiskSpill = true;
          const neededMB = Math.min(
            this.maxWorkMemCeilingMB,
            Math.ceil((sortSpaceUsedKb * 1.5) / 1024)
          );

          violations.push({
            nodeType: 'Sort',
            severity: 'CRITICAL',
            issue: `External Merge Sort Disk Spill detected: ${sortSpaceUsedKb} kB spilled to temporary files via "${sortMethod}". Spikes NVMe I/O and destroys query p99.`,
            remedy: `Increase transaction-scoped work_mem to at least ${neededMB}MB via SET LOCAL work_mem, or eliminate sort via presorted B-Tree index.`,
            recommendedGucSql: `SET LOCAL work_mem = '${neededMB}MB';`,
            metrics: {
              sortMethod,
              sortSpaceType,
              sortSpaceUsedKb,
              actualRows,
              planRows,
            },
          });
        }

        // Check for Top-N Heapsort Preservation
        if (sortMethod.includes('top-N heapsort')) {
          isTopNPreserved = true;
        } else if (queryHasLimit && !hasDiskSpill && actualRows > 1000) {
          violations.push({
            nodeType: 'Sort',
            severity: 'WARNING',
            issue: `Query contains LIMIT clause but executed unbounded "${sortMethod}" instead of bounded "top-N heapsort". Indicates LIMIT pushdown barrier (e.g. unpushed window function or CTE).`,
            remedy: `Push LIMIT into subquery or eliminate intermediate blocking nodes to enable O(K) memory Top-N Heapsort.`,
            metrics: {
              sortMethod,
              sortSpaceType,
              sortSpaceUsedKb,
              actualRows,
              planRows,
            },
          });
        }
      }

      // 2. Audit Incremental Sort Nodes (PostgreSQL 13+)
      if (nodeType === 'Incremental Sort') {
        hasIncrementalSort = true;
        const presortedKey = node['Presorted Key'] ?? '';
        const fullSortGroups = node['Full-sort Groups'] ?? 0;
        const presortedGroups = node['Pre-sorted Groups'] ?? 0;
        const sortSpaceType = node['Sort Space Type'] ?? '';
        const sortSpaceUsedKb = node['Sort Space Used'] ?? 0;

        if (sortSpaceUsedKb > maxSortSpaceUsedKb) {
          maxSortSpaceUsedKb = sortSpaceUsedKb;
        }

        if (sortSpaceType === 'Disk') {
          hasDiskSpill = true;
          violations.push({
            nodeType: 'Incremental Sort',
            severity: 'CRITICAL',
            issue: `Incremental Sort spilled ${sortSpaceUsedKb} kB to disk during group sort. Prefix key "${presortedKey}" has degenerate low cardinality or extreme skew.`,
            remedy: `Ensure prefix keys have high entropy or raise transaction work_mem to fit the largest prefix group.`,
            recommendedGucSql: `SET LOCAL work_mem = '${Math.min(this.maxWorkMemCeilingMB, Math.ceil((sortSpaceUsedKb * 1.5) / 1024))}MB';`,
            metrics: {
              presortedKey,
              fullSortGroups,
              presortedGroups,
              sortSpaceType,
              sortSpaceUsedKb,
              actualRows,
            },
          });
        }
      }

      // 3. Audit Parallel Gather Merge Sort Memory Multiplication
      if (nodeType === 'Gather Merge') {
        const workersPlanned = node['Workers Planned'] ?? 0;
        const workersLaunched = node['Workers Launched'] ?? workersPlanned;

        if (workersLaunched > 2 && maxSortSpaceUsedKb > 32768) {
          const totalEstimatedSortMemMB = Math.round(((workersLaunched + 1) * maxSortSpaceUsedKb) / 1024);
          violations.push({
            nodeType: 'Gather Merge',
            severity: 'WARNING',
            issue: `Gather Merge active with ${workersLaunched} workers. Peak sort memory multiplies across workers (~${totalEstimatedSortMemMB}MB total), risking host OOM SIGKILL.`,
            remedy: `Calibrate max_parallel_workers_per_gather or bound work_mem for parallel query paths.`,
            recommendedGucSql: `SET LOCAL max_parallel_workers_per_gather = 2;`,
            metrics: {
              workersAllocated: workersLaunched,
              actualRows,
              planRows,
            },
          });
        }
      }

      // Recursively audit child plan nodes
      if (Array.isArray(node.Plans)) {
        for (const child of node.Plans) {
          traverse(child, node);
        }
      }
    };

    traverse(rootPlan, null);

    if (queryHasLocaleSort && maxSortSpaceUsedKb > 16384) {
      hasLocaleCollationPenalty = true;
      violations.push({
        nodeType: 'Sort',
        severity: 'INFO',
        issue: `Heavy text sorting detected without explicit COLLATE "C". Invokes libc strcoll() on every comparison, burning up to 85% CPU in string normalization.`,
        remedy: `Add COLLATE "C" to ORDER BY text columns or create index with COLLATE "C" for single-instruction binary memcmp comparisons.`,
        recommendedIndexSql: `-- Add COLLATE "C" to sort column in index definition\nCREATE INDEX CONCURRENTLY idx_fast_sort ON tbl (str_col COLLATE "C" DESC);`,
        metrics: {
          sortSpaceUsedKb: maxSortSpaceUsedKb,
        },
      });
    }

    const calculatedWorkMemMB = Math.min(
      this.maxWorkMemCeilingMB,
      Math.max(this.defaultWorkMemMB, Math.ceil((maxSortSpaceUsedKb * 1.5) / 1024))
    );

    return {
      isCompliant: !hasDiskSpill && violations.filter((v) => v.severity === 'CRITICAL').length === 0,
      hasDiskSpill,
      isTopNPreserved,
      hasIncrementalSort,
      hasLocaleCollationPenalty,
      violations,
      suggestedWorkMemMB: calculatedWorkMemMB,
    };
  }
}
```

### 4.1 Go (`jackc/pgx/v5`): Sort Governor & Keyset Paginator

```go
// sort_governor.go
package db

import (
	"context"
	"encoding/json"
	"fmt"
	"strings"
	"time"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// SortPlanViolation captures sort anomalies from EXPLAIN JSON
type SortPlanViolation struct {
	NodeType        string  `json:"node_type"`
	Severity        string  `json:"severity"`
	Issue           string  `json:"issue"`
	SortMethod      string  `json:"sort_method,omitempty"`
	SortSpaceType   string  `json:"sort_space_type,omitempty"`
	SortSpaceUsedKb float64 `json:"sort_space_used_kb,omitempty"`
}

// SortGovernor enforces zero disk spill invariants on sorted queries
type SortGovernor struct {
	Pool *pgxpool.Pool
}

// ExecuteWithCalibratedSortMem runs a query inside a transaction with calibrated work_mem
func (g *SortGovernor) ExecuteWithCalibratedSortMem(
	ctx context.Context,
	workMemMB int,
	fn func(tx pgx.Tx) error,
) error {
	tx, err := g.Pool.BeginTx(ctx, pgx.TxOptions{IsoLevel: pgx.ReadCommitted})
	if err != nil {
		return fmt.Errorf("begin tx: %w", err)
	}
	defer tx.Rollback(ctx)

	setSQL := fmt.Sprintf("SET LOCAL work_mem = '%dMB'", workMemMB)
	if _, err := tx.Exec(ctx, setSQL); err != nil {
		return fmt.Errorf("set local work_mem: %w", err)
	}

	if err := fn(tx); err != nil {
		return err
	}

	return tx.Commit(ctx)
}

// AuditSortPlan asserts that an EXPLAIN plan does not spill sort runs to disk
func (g *SortGovernor) AuditSortPlan(ctx context.Context, querySQL string, args ...any) error {
	explainSQL := fmt.Sprintf("EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) %s", querySQL)

	ctxTimeout, cancel := context.WithTimeout(ctx, 15*time.Second)
	defer cancel()

	var rawJSON []byte
	if err := g.Pool.QueryRow(ctxTimeout, explainSQL, args...).Scan(&rawJSON); err != nil {
		return fmt.Errorf("explain query failed: %w", err)
	}

	var plans []struct {
		Plan map[string]any `json:"Plan"`
	}
	if err := json.Unmarshal(rawJSON, &plans); err != nil || len(plans) == 0 {
		return fmt.Errorf("parse explain json failed: %w", err)
	}

	var externalMergeSortFound bool
	var spilledKb float64

	var inspect func(node map[string]any)
	inspect = func(node map[string]any) {
		nodeType, _ := node["Node Type"].(string)

		if nodeType == "Sort" || nodeType == "Incremental Sort" {
			sortSpaceType, _ := node["Sort Space Type"].(string)
			sortMethod, _ := node["Sort Method"].(string)
			sortSpaceUsed, _ := node["Sort Space Used"].(float64)

			if sortSpaceType == "Disk" || strings.Contains(sortMethod, "external merge") {
				externalMergeSortFound = true
				spilledKb += sortSpaceUsed
			}
		}

		if children, ok := node["Plans"].([]any); ok {
			for _, c := range children {
				if childMap, ok := c.(map[string]any); ok {
					inspect(childMap)
				}
			}
		}
	}

	inspect(plans[0].Plan)

	if externalMergeSortFound {
		return fmt.Errorf(
			"SORT VIOLATION: External Merge Sort Disk Spill detected (spilled %.0f kB to disk). Requires index ordering or calibrated work_mem",
			spilledKb,
		)
	}

	return nil
```

```python
import json
import logging
from typing import Any, Dict, Optional, Tuple
from sqlalchemy.ext.asyncio import AsyncSession
from sqlalchemy import text

logger = logging.getLogger("sort_sentinel")

class SortPlanViolationError(Exception):

class AsyncSortSentinel:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def execute_with_calibrated_sort(
        self,
        query_sql: str,
        params: Dict[str, Any],
        work_mem_mb: int = 32,
    ) -> Any:
        """Executes query within transaction-scoped work_mem to guarantee in-memory sort."""
        async with self.session.begin():
            await self.session.execute(text(f"SET LOCAL work_mem = '{work_mem_mb}MB'"))
            result = await self.session.execute(text(query_sql), params)
            return result.fetchall()

    async def verify_zero_spill_plan(self, query_sql: str, params: Dict[str, Any]) -> None:

        result = await self.session.execute(text(explain_sql), params)
        row = result.scalar()
        parsed = json.loads(row) if isinstance(row, str) else row
        root_plan = parsed[0]["Plan"] if isinstance(parsed, list) else parsed["Plan"]

        def check_node(node: Dict[str, Any]) -> None:
```

### 4.3 Rust (`sqlx`): Zero-Spill Keyset Sort Streamer

```rust
// sort_streamer.rs
use sqlx::{PgPool, Transaction, Postgres};
use serde_json::Value;

#[derive(Debug, thiserror::Error)]
pub enum SortGuardError {
    #[error("Database error: {0}")]
    Db(#[from] sqlx::Error),
    #[error("External merge sort disk spill: {0} kB spilled to temp files")]
    DiskSpill(f64),
    #[error("Invalid EXPLAIN JSON payload")]
    InvalidJson,
}

pub struct SortStreamer<'a> {
    tx: Transaction<'a, Postgres>,
}

impl<'a> SortStreamer<'a> {
    pub async fn begin_calibrated(pool: &'a PgPool, work_mem_mb: u32) -> Result<Self, SortGuardError> {
        let mut tx = pool.begin().await?;
        let set_sql = format!("SET LOCAL work_mem = '{}MB'", work_mem_mb);
        sqlx::query(&set_sql).execute(&mut *tx).await?;
        Ok(Self { tx })
    }

    pub async fn assert_zero_spill(&mut self, query_sql: &str) -> Result<(), SortGuardError> {
        let explain_sql = format!("EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) {}", query_sql);
        let row: (Value,) = sqlx::query_as(&explain_sql)
            .fetch_one(&mut *self.tx)
            .await?;

        let root = row.0.get(0)
            .and_then(|v| v.get("Plan"))
            .ok_or(SortGuardError::InvalidJson)?;

        Self::traverse_node(root)?;
        Ok(())
    }

    fn traverse_node(node: &Value) -> Result<(), SortGuardError> {
        if let Some(node_type) = node.get("Node Type").and_then(|v| v.as_str()) {
            if node_type == "Sort" || node_type == "Incremental Sort" {
                let space_type = node.get("Sort Space Type").and_then(|v| v.as_str()).unwrap_or("");
                let method = node.get("Sort Method").and_then(|v| v.as_str()).unwrap_or("");
                let space_used = node.get("Sort Space Used").and_then(|v| v.as_f64()).unwrap_or(0.0);

                if space_type == "Disk" || method.contains("external merge") {
                    return Err(SortGuardError::DiskSpill(space_used));
                }
            }
        }

        if let Some(plans) = node.get("Plans").and_then(|v| v.as_array()) {
            for child in plans {
                Self::traverse_node(child)?;
            }
        }

        Ok(())
    }

    pub async fn commit(self) -> Result<(), SortGuardError> {
        self.tx.commit().await.map_err(SortGuardError::Db)
    }
}
```

## Conclusion & Operational Discipline

1. **Zero Tolerance for External Merge Sort Spills**: Never allow queries to write temporary sort runs to disk in production (`Sort Space Type: Disk`). Spills destroy NVMe write endurance, trigger IOPS throttling, and induce catastrophic tail latency cliffs.
2. **Preserve Top-N Heapsort on Bounded Queries**: When designing endpoints with `LIMIT`, ensure execution plans employ bounded Top-N Heapsort ($O(K)$ space) or zero-sort index streaming, never unbounded full table sorts.
3. **Exploit Incremental Sort on Composite Criteria**: When adding secondary sort dimensions to already-indexed prefix columns, verify that PostgreSQL 13+ `Incremental Sort` activates cleanly without degenerate group memory bloat.
4. **Enforce Keyset Seek Pagination**: Forbid large `OFFSET` values in customer-facing APIs and internal data scrapers. Keyset cursor seek queries execute with constant memory and deterministic millisecond latency.
